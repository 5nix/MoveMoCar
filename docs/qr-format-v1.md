# 挪车码配置格式 M1

本文档定义 MoveMoCar 正式发布前确定的第一版二维码配置格式。M1 面向长期打印使用，设计目标依次为：发布后保持二维码可解析、降低二维码密度、允许增量扩展、在通知配置异常时恢复备用号码。

开发期曾使用的 `#n=<Base64URL>&cfg=<Base64URL(JSON)>` 不属于发布协议，也不保留兼容性。

## URL 结构

```text
https://example.com/#M1.<core>.<codec><channels>
```

- `M1` 是主格式版本。只有发生无法向前兼容的变化时才增加主版本。
- `core` 是未压缩的 CBOR 核心段，经无填充 Base32 编码。
- `codec` 为 `U` 时，渠道段是未压缩 CBOR；为 `D` 时，是 RFC 1951 DEFLATE 数据。
- `channels` 是渠道段经无填充 Base32 编码后的内容。
- 所有配置均位于 URL Fragment 中，不会作为 HTTP 请求目标发送给静态站点。

Base32 必须使用 RFC 4648 的大写字母表 `A-Z2-7`，不得包含 `=` 填充。解码器必须拒绝小写、非字母表字符、非零尾随位和非规范编码。

## CBOR 规则

M1 使用 RFC 8949 CBOR，并要求编码器产生 Core Deterministic Encoding：

- 整数和长度必须使用最短表示；
- 数组、Map、字符串和字节串必须使用确定长度；
- 不使用 CBOR Tag 或 `undefined`；
- Map 不得包含重复键；
- 协议字段使用无符号整数编号；
- 未识别的扩展键由旧解码器忽略。

以下结构采用 CDDL 风格表示，但本文档不依赖外部 Schema 文件。

```text
core = [
  phone: bstr,
  vehicle: tstr,
  ? extensions: { * uint => any }
]

channels = [*5 channel]

channel = bark / wxpusher / ntfy / webhook / future-channel

bark = [0, token, ? { ? 0: https-url, * uint => any }]
wxpusher = [1, token, ? { * uint => any }]
ntfy = [2, token, ? { ? 0: https-url, * uint => any }]
webhook = [3, https-url, ? webhook-options]
future-channel = [uint, any, ? { * uint => any }]

webhook-options = {
  ? 0: 0 / 1 / 2,
  ? 1: { * tstr => tstr },
  ? 2: json-value,
  ? 3: uint,
  ? 4: [uint, uint],
  * uint => any
}

token = tstr / bstr
https-url = tstr
```

## 核心段

核心段始终保持未压缩并位于渠道段之前。页面无法解析、解压或识别渠道段时，仍应尝试独立读取核心段中的备用号码。

### 电话号码

电话号码仅包含十进制数字，使用压缩十进制表示：

- 每个字节的高、低半字节各保存一位数字；
- 数字顺序从高半字节到低半字节；
- 奇数位号码最后一个字节的低半字节使用 `0xF` 填充；
- `0xA` 至 `0xE` 不合法，`0xF` 只能出现在最后一个低半字节；
- 电话号码最长 15 位，与国际 E.164 的最大数字位数保持一致；页面只保留十进制数字，不在编码中保存 `+`、空格或分隔符。

例如 `139` 编码为字节串 `0x13 0x9F`。

### 车辆标识

车辆标识是 UTF-8 文本字符串。M1 不限定车牌国家、字符集或具体格式；生成器可以在展示结果中做空格清理和大小写规范化。

### 核心扩展

第三个数组元素是可选的整数键 Map。当前分配：

| 键 | 含义 | 值 |
| ---: | --- | --- |
| 0 | 车主通知语言 | 语言编号，无符号整数 |

语言编号按追加方式保持稳定：`0` 简体中文、`1` English、`2` 繁體中文、`3` Español、`4` Français、`5` Deutsch、`6` Italiano、`7` Português (Brasil)、`8` 日本語、`9` 한국어。简体中文是默认值，编码器必须省略语言扩展；缺少该扩展的解码结果也必须使用简体中文。扫码者界面语言由扫码者浏览器决定，不受此字段影响。

未来新增语言只能追加编号，不能重排已经分配的编号。其他核心能力应分配新键，旧解码器必须忽略未知键。

## 通知渠道

渠道类型编号如下：

| 编号 | 渠道 |
| ---: | --- |
| 0 | Bark |
| 1 | WxPusher |
| 2 | ntfy |
| 3 | 通用 Webhook |

渠道名称只服务于生成器界面，不参与运行时通知，因此不写入二维码。

旧解码器遇到未知渠道编号时应跳过该渠道，并继续处理能够识别的渠道。没有任何可识别渠道时，页面进入配置异常预案并使用核心段备用号码。

### Token 压缩

`token` 可以是文本或字节串：

- 文本表示无法进一步压缩的原始值；
- 字节串表示原字符串可以被规范 Base64URL 无损还原；
- Bark 字节串直接还原为 Base64URL；
- WxPusher 字节串还原后加上 `SPT_`；
- ntfy 字节串还原后加上 `mmc_`。

只有重新编码后与原字符串完全一致时才能使用字节串形式，否则必须原样保存为文本。

### HTTPS 地址

M1 中的 Bark Server、ntfy Server 和 Webhook URL 均要求 HTTPS。二维码内省略固定的 `https://` 前缀，解码时恢复；其余 authority、端口、路径、查询参数必须原样保留。

### Webhook 选项

Webhook 请求方法编号：

| 编号 | 方法 |
| ---: | --- |
| 0 或省略 | POST |
| 1 | PUT |
| 2 | PATCH |

请求头、请求体模板、超时时间和成功状态范围只有在实际配置时才写入。JSON 值只允许有限深度的字符串、有限数值、布尔值、`null`、数组和字符串键对象。

## 压缩

核心段永不压缩。渠道段同时计算未压缩 CBOR 与最高等级 DEFLATE；只有 DEFLATE 至少节省 8 个字节时才使用 `D`，否则使用 `U`。

解码器必须同时支持 `U` 和 `D`，并在解压前后分别执行大小限制。不得根据输入内容尝试未声明的压缩算法。

## 解析限制

当前实现使用以下上限：

- Fragment 最长 4096 个字符；
- 核心段 Base32 最长 512 个字符；
- 单个 CBOR 段解码或解压后最大 8192 字节；
- CBOR 最大嵌套深度为 16 层，单个数组或 Map 最多 100 项；
- 核心和渠道扩展 Map 最多 16 个键；
- 通知渠道总数为 0 至 5 个；0 个表示仅保留电话联系；
- Webhook JSON 最大嵌套深度为 12 层。

这些限制属于 M1 的防御性解析要求。实现可以使用更低的生成上限保证实体二维码易于扫描，但不得接受无限制输入。

## 兼容规则

M1 发布后遵守以下规则：

1. 已分配字段和渠道编号不得改变含义。
2. 新增可选能力使用未分配的整数键。
3. 旧解码器忽略未知扩展键和未知渠道。
4. 必填字段变化、编码语义变化或压缩体系变化必须升级为新的主格式版本。
5. 页面应永久保留所有已经公开发布的主格式解码器。
6. 每个主格式必须保留固定测试向量、异常输入测试和实体二维码密度回归测试。

## 固定测试向量

语义配置：

```json
{
  "v": 1,
  "car": "浙A12345",
  "num": "13900000000",
  "pushes": [
    { "type": "bark", "key": "test-bark-key" }
  ]
}
```

M1 编码：

```text
M1.QJDBHEAAAAAA62PGWWMUCMJSGM2DK.UQGBAA3LUMVZXILLCMFZGWLLLMV4Q
```

编码器对该语义配置必须产生完全相同的字节和文本；解码器必须还原相同的运行时配置。

## 完整性与安全边界

M1 不额外加入可伪造的“防篡改校验码”。物理污损由二维码自身的 Reed–Solomon 纠错处理；链接截断和内容损坏由规范 Base32、确定长度 CBOR、严格字段校验和分段解析发现。

任何未持有秘密的校验值都不能阻止攻击者替换整个二维码。M1 也不加密车主号码或推送凭据：静态页面必须能够读取它们才能发起通知。公开托管页面不得加载能够读取 Fragment 的第三方脚本；需要隐藏凭据或服务器级限流时，应改用后端或 Serverless 服务。
